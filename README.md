## Задача 2: Выбор типа платформы

* **1. Высоконагруженная база данных MySQL, критичная к отказу**
  - **Выбор:** Физические сервера (Bare Metal).
  - **Критерии:** Высоконагруженная СУБД критична к задержкам дисковой подсистемы (IOPS) и пропускной способности оперативной памяти. Физическое железо полностью исключает накладные расходы (оверхед) гипервизора. Также это изолирует базу данных от эффекта «шумных соседей» (когда другие ВМ на хосте забирают общие ресурсы). Отказоустойчивость при этом обеспечивается на уровне архитектуры самой БД (кластеризация, репликация).

* **2. Различные web-приложения**
  - **Выбор:** Виртуализация уровня ОС (Контейнеризация / Docker / Kubernetes).
  - **Критерии:** Микросервисы и классические веб-приложения зачастую неравномерно или экономно потребляют ресурсы. Контейнеризация обеспечивает максимальную плотность размещения приложений на одном сервере без затрат памяти на запуск изолированных гостевых ОС. Контейнеры запускаются мгновенно, изолируют конфликтующие зависимости (например, разные версии Python/Node.js) и идеально подходят для автоматизации процессов CI/CD и горизонтального масштабирования.

* **3. Windows-системы для использования бухгалтерским отделом**
  - **Выбор:** Паравиртуализация (Аппаратная виртуализация).
  - **Критерии:** Для работы бухгалтерии (1С, офисные пакеты, терминальный доступ RDP) требуются полноценные графические операционные системы семейства Windows. Запустить нативную графическую Windows внутри стандартных Linux-контейнеров невозможно, поэтому требуется полноценный гипервизор. Паравиртуализация предоставляет строгую изоляцию конфиденциальных данных, а также удобные инструменты администрирования: создание снапшотов (снимков системы) перед обновлениями 1С и централизованный бэкап всей ОС.

* **4. Системы, выполняющие высокопроизводительные расчёты на GPU**
  - **Выбор:** Физические сервера (Bare Metal) *ИЛИ* Паравиртуализация с технологией GPU Passthrough.
  - **Критерии:** Передача огромных массивов данных при расчете нейросетей или рендеринге между CPU, RAM и графическим процессором требует максимальной пропускной способности шины PCIe. Любая эмуляция видеокарты гипервизором критически снизит производительность. Идеальный выбор — физическое железо. Если вычисления запускаются в облаке, выбирается паравиртуализация со сквозным пробросом видеокарты (GPU Passthrough) напрямую в ВМ, что минимизирует потери производительности до незначительных 2–5%.

## Задача 3: Выбор системы управления виртуализацией

* **Сценарий 1 (100 ВМ Linux/Windows, преимущественно Windows-инфраструктура, балансировщики, репликация, бэкапы):**
  - **Выбор:** Microsoft Hyper-V (в составе Windows Server Datacenter) + System Center Virtual Machine Manager (VMM) / Windows Admin Center.
  - **Обоснование:** Родной гипервизор от Microsoft обеспечит идеальную совместимость и производительность для Windows-ориентированной инфраструктуры. Лицензирование редакции Datacenter экономически выгодно при высокой плотности ВМ Windows на физических хостах. Функционал репликации (Hyper-V Replica) и механизмы отказоустойчивости встроены «из коробки», а экосистема Microsoft предлагает нативную интеграцию с лидирующими решениями резервного копирования (например, Veeam).

* **Сценарий 2 (Производительное бесплатное open source-решение для 20-30 серверов Linux и Windows):**
  - **Выбор:** Proxmox Virtual Environment (Proxmox VE).
  - **Обоснование:** Proxmox VE — это мощная бесплатная платформа корпоративного уровня с открытым исходным кодом. В её основе лежит гипервизор KVM, обеспечивающий отличную производительность для Linux и Windows. Она имеет удобный веб-интерфейс, поддерживает кластеризацию для 20–30 серверов, живую миграцию ВМ, создание программных хранилищ (ZFS, Ceph) и содержит встроенный инструмент бэкапов (Proxmox Backup Server) без необходимости покупки коммерческих лицензий.

* **Сценарий 3 (Бесплатное, максимально совместимое и производительное решение для Windows-инфраструктуры):**
  - **Выбор:** Роль Hyper-V на базе бесплатной ознакомительной (Evaluation) версии Windows Server или использование MS Hyper-V Server.
  - **Обоснование:** Использование родного гипервизора Microsoft гарантирует отсутствие проблем с совместимостью служб Windows (таких как Active Directory, IIS, MS SQL). Гостевые ОС Windows содержат нативные компоненты интеграции для Hyper-V, что обеспечивает наивысшую производительность дисков и сети по сравнению со сторонними бесплатными гипервизорами.

* **Сценарий 4 (Рабочее окружение для тестирования продукта на нескольких дистрибутивах Linux):**
  - **Выбор:** Oracle VirtualBox в связке с Vagrant, либо локальный Docker.
  - **Обоснование:** Для локального тестирования на компьютере инженера VirtualBox является бесплатным кроссплатформенным стандартом. Утилита Vagrant позволяет описывать конфигурации тестовых машин кодом и поднимать дистрибутивы (Ubuntu, CentOS, Debian) одной командой `vagrant up`. Если графическая оболочка ОС не требуется, более производительным решением будет Docker, так как запуск Linux-контейнеров происходит мгновенно и практически не расходует ресурсы локального процессора и RAM.

## Задача 4: Гетерогенная среда виртуализации

### Возможные проблемы и недостатки:
1. **Сложность управления («зоопарк» систем):** Отсутствие единой панели мониторинга и управления. Инженерам приходится использовать разные консоли, API и CLI-инструменты для каждой платформы.
2. **Проблемы переносимости (Vendor Lock-in):** Сложно осуществить миграцию ВМ между разными гипервизорами (например, конвертация дисков из формата VMware `vmdk` в формат KVM `qcow2` или Hyper-V `vhdx`). Это связано с рисками повреждения данных и требует простоя сервисов.
3. **Фрагментация бэкапов и мониторинга:** Сложно построить централизованную систему резервного копирования и мониторинга метрик, приходится внедрять и поддерживать разные программные модули под каждую платформу.
4. **Повышенные требования к квалификации персонала:** Команда администрирования и DevOps должна обладать глубокими компетенциями во всех используемых технологиях, что усложняет поиск кадров и увеличивает бюджет на ФОТ.

### Способы минимизации рисков:
- **Внедрение инфраструктуры как кода (IaC):** Использование **Terraform** со спецификациями под каждую платформу позволяет стандартизировать и описывать создание ресурсов единым подходом.
- **Централизованный мониторинг и логирование:** Развертывание сквозных систем сбора метрик и логов (Prometheus + Grafana, векторные сборщики логов), собирающих данные со всех гипервизоров в единую панель.
- **Унификация на уровне контейнеризации:** Перевод приложений в контейнеры (Docker/Kubernetes). В таком случае среда виртуализации становится лишь нижележащим слоем (инфраструктурой), а сами приложения работают везде абсолютно одинаково, изолируясь от особенностей конкретных гипервизоров.

### Личный выбор архитектора: Создавал бы я гетерогенную среду?
**Нет, за исключением случаев крайней необходимости.**

В инженерной практике всегда следует стремиться к **гомогенности (однородности) среды**. Моноплатформенная инфраструктура значительно проще в поддержке, автоматизации и эксплуатации. Гетерогенную среду стоит создавать только под давлением внешних факторов, таких как необходимость жесткой экономии (тесты на Proxmox, прод на VMware), реализация гибридного облака (свой ЦОД + Yandex Cloud) или в процессе слияния инфраструктур разных компаний.
